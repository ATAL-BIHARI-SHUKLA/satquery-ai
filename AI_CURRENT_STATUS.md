# SatQuery AI - Current Status Audit

This document is a complete current status audit of SatQuery AI for the next development phase.

## 1. LIVE CHAT
- **Query Submission**: The `ConversationInput` component accepts a text query and/or an image file. It triggers the `onSubmit` callback when the user clicks the "Ask" button or presses `Enter`.
- **Frontend Function/API**: `handleQuerySubmit` in `AnalysisWorkspace.jsx` is called, which invokes `api.submitQuery` (`POST /api/query`).
- **Response Format**: The response is returned as a single JSON object (HTTP POST request) containing the execution results. It is **not streamed**.
- **Conversation Persistence**: Yes. The backend (`conversation_store.add_message` in `backend/app/services/conversation.py`) saves both the user's message and the assistant's reply (as a stringified JSON object).
- **Multiple Follow-ups**: Yes. Users can ask follow-up questions in the same conversation. The `conversation_id` is passed with each subsequent query, maintaining state in the database.
- **WebSocket/SSE**: There is **no** WebSocket or Server-Sent Events (SSE) implementation. Communication relies entirely on standard REST HTTP calls.

## 2. QUERY BACKEND
The query logic is housed in `backend/app/api/routes/query.py`.
- **Endpoint**: `POST /api/query`
- **Request Schema**: `QueryRequest` (contains `query`, `filename`, `conversation_id`, and `context`).
- **Response Schema**: `QueryResponse` (contains `success`, `query`, `message`, `task`, `context_status`, `resolved_images`, and the full `execution` result dictionary).
- **Query Router/Task Detection**: Performed by `route_query` in `backend/app/services/router.py`. It uses simple keyword/regex matching (e.g., checking for "sar", "change", "where is", "development") to map the text query to a specific `TaskType`.
- **Persistence**: Managed by `conversation_store`. It stores the raw text, resolves contexts, saves the execution results (`add_analysis_result`), and saves the final message (`add_message`).
- **Error Handling**: Uses FastAPI's `HTTPException` for missing inputs (400) or missing conversations (404).

## 3. AI ANALYSIS
The AI model registry exists (`backend/app/models/registry.py`) but all actual deep learning inference components are currently either placeholders or entirely mocked. The dispatch happens in `backend/app/services/executor.py`.

- **VQA**: **MOCK** (`execute_vqa` returns a hardcoded string)
- **Captioning**: **MOCK** (`execute_captioning` returns a hardcoded string)
- **Visual Grounding**: **MOCK** (`execute_grounding` returns a hardcoded string)
- **Optical + SAR**: **MOCK** (`execute_optical_sar_analysis` returns a hardcoded string)
- **Geo Analysis**: **MOCK** (`execute_geo_analysis` returns a hardcoded string)
- **Change Detection**: **PARTIAL**. Uses `rasterio` in `backend/app/services/change_detection.py` to read a 512x512 central window of two GeoTIFFs, normalize them, and calculate simple absolute pixel differences. There is no ML model involved.
- **Land-cover Analysis**: **PARTIAL**. Uses `rasterio` in `backend/app/services/land_cover.py` to calculate traditional non-ML spectral indices (NDVI, NDWI, NDBI proxy) from the Cloud Optimized GeoTIFF bands.
- **Specialist Model Execution**: **MISSING**. `registry.find_model_for_task` exists but there are no real model implementations registered (only empty base classes).
- **RS-LLaVA / VLM**: **MISSING**. No Vision-Language Model is connected or configured.
- **Model Adapters**: **MISSING**. No adapters implemented.
- **Inference Client**: **MISSING**. No local or cloud inference client is set up.

## 4. RESULT UI
The result UI components are `AnalysisPanel.jsx`, `ActiveAnalysisState.jsx`, and `ConversationInput.jsx`.

- **What is REAL**:
  - The map center and bounding radius (handled via Leaflet).
  - The STAC Satellite metadata fetched from the backend (Provider name, Cloud cover percentage, Selected Date).
  - The user's query and the chat history (fetched from DB).
- **What is MOCK / HARDCODED**:
  - The "Image Metadata" overlay on uploaded images in `ActiveAnalysisState.jsx` is hardcoded (e.g., `Type: Optical / Multispectral`, `Resolution: ~10m/px`, and today's date).
  - The text generated in the chat interface is either a mocked string (for VQA/Captioning) or a rules-based string template generated by `AnswerGeneratorService` (for location development).
  - Execution summary, confidence UI (high/medium/low based strictly on cloud cover rules), and evidence UI just render the JSON dumped by the backend rules engine.
- **Loading / Error States**: Handled realistically using React state (`loading`, `satelliteLoading`, `satelliteError`).

## 5. DATA FLOW
Trace of a complete query (Location Development Workflow):
1. User types query and submits via `ConversationInput.jsx`.
2. `AnalysisWorkspace.jsx` (`handleQuerySubmit`) sends `POST /api/query`.
3. Backend `query.py` stores the user message in DB, then passes inputs to `router.py`.
4. `router.py` classifies the query as `LOCATION_DEVELOPMENT_ANALYSIS` based on keywords ("development", etc.).
5. **[REAL FLOW ENDS HERE]** The router calls `executor.py:execute_location_development`.
6. Executor fetches historical COGs (real STAC URLs).
7. Executor runs `rasterio` script to do simple band math (NDVI/pixel difference) instead of actual ML models.
8. `AnswerGeneratorService` fills out a hardcoded text template using the band math results.
9. Backend saves this JSON as an assistant message in the DB.
10. Backend returns JSON to frontend.
11. Frontend parses the JSON and `AnalysisPanel.jsx` renders the text template.

## 6. BIGGEST BLOCKER
The entire "AI" layer does not exist. SatQuery AI currently acts as a keyword-based router that triggers basic GDAL/rasterio scripts for NDVI and pixel-differencing. There is no natural language understanding, no visual question answering, and no computer vision models deployed.

## 7. RECOMMENDED NEXT SINGLE TASK
Implement the **Inference Client and Model Adapter architecture**. Select and integrate a single baseline Vision-Language Model (like LLaVA or a cloud equivalent like Gemini Pro Vision) so that the application can begin processing actual multimodal prompts instead of falling back to keyword-based mocks.
